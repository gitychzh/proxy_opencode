# v2 规划：槽位池网关（双网关并行上线）

> 状态：**待确认**。本文只做规划，确认后再执行。
> 目标：**旧部署一行不动**，新增一份「单网关 + 多出口槽位」的新形态，跑在 ECS 上，
> 走 `llm2.223722.xyz`，双网关并行观察，稳定后再下线旧模式。

---

## 0. 目标与非目标

**目标**
- 旧链路（`llm.223722.xyz` → LB:7892 → 4 桶网关）**完全不改**
- 新链路：`llm2.223722.xyz` → 新网关（唯一一份代码，伪造逻辑集中在此）→ N 个出口槽位
- 容器化部署，摆脱「4 台异构机器 4 种启动方式」
- 凭证不变（沿用现有 `ADMIN_API_KEYS`，见仓库外 `scripts_local/secrets.env`）
- 为「以后很多手机桶」留出扩展路径

**非目标**
- 不改旧桶的任何配置
- 不买商用代理（用你自己的真实出口）
- 不追求一次铺满，先小规模跑稳

## 1. 已探明的事实（本轮实测）

### 1.1 ECS 环境

| 项 | 值 | 影响 |
| --- | --- | --- |
| 规格 | **2 vCPU / 1.6 GB RAM / 40 GB 盘（用 15%）** | **内存是硬约束** |
| Swap | **无** | 建议先加 1–2 GB |
| OS | Ubuntu 24.04 / kernel 6.8 | — |
| Docker | 29.1.3，daemon active | ✅ 可用 |
| docker compose | **缺插件** | 需 `apt install docker-compose-v2` |
| 已占端口 | 7892（LB）、80/443（Caddy） | 新网关用 **8793** |
| 内存占用 | journal 75M / tailscaled 69M / dockerd 63M / LB 36M / cloudflared 34M，**可用 ~1.06 GB** | — |
| Tailscale | `100.90.84.65` | ✅ 到各节点已打通 |

### 1.2 公网入口怎么接的

```
llm.223722.xyz  --(Cloudflare)-->  cloudflared 隧道 zen-gw  -->  localhost:7892 (LB)
```
- 隧道配置：`/etc/cloudflared/config.yml`，`ingress: llm.223722.xyz → http://localhost:7892`
- 另有 `zen.223722.xyz` → Caddy → 127.0.0.1:7892

**新域名接入方式（推荐）**：给同一条隧道加一条 ingress + 一个 DNS 记录：
```bash
cloudflared tunnel route dns zen-gw llm2.223722.xyz   # 自动建 CNAME
# 然后在 config.yml 的 ingress 里加：
#   - hostname: llm2.223722.xyz
#     service: http://localhost:8793
systemctl restart cloudflared
```
→ 复用现有隧道与证书，**不新开端口、不动 Caddy、不申请新证书**。

### 1.3 关键前提验证：槽位出口能不能建

| 节点 | 从 ECS 可达 | 机制 | 备注 |
| --- | --- | --- | --- |
| **ECS 自身** | — | 直连 | **0 跳，免费的第 5 份配额**，务必用作 slot 0 |
| owin10 | ✅ `2222` | Windows OpenSSH | 可直接做 SSH 动态转发槽 |
| ubuntu26 | ✅ `2222` | Linux，**已装 autossh** | 最省事 |
| phone115 | ✅ `2222` | Termux sshd | 可直接做槽 |
| **win10-local** | ❌ `22` 关闭，**本机没装 sshd** | — | **需要决策**（见 D1） |

⚠️ **ECS 上目前没有任何 SSH 私钥**（只有 `authorized_keys`）→ 需生成密钥并授权到各节点。

## 2. 目标架构

```
用户 → llm2.223722.xyz  (Cloudflare Tunnel zen-gw)
         → ECS:8793  新网关（唯一一份代码，含伪造/标记注入）
              ├─ slot 0  直连          → Zen   (ECS 自己出口，0 跳)
              ├─ slot 1  socks5://127.0.0.1:10801 → ubuntu26 → Zen
              ├─ slot 2  socks5://127.0.0.1:10802 → owin10   → Zen
              ├─ slot 3  socks5://127.0.0.1:10803 → phone115 → Zen
              ├─ slot 4  socks5://127.0.0.1:10804 → win10-local → Zen   (待 D1 决策)
              └─ slot N  ... 以后每台手机加一条
```

- **槽位 = 出口 IP**（与配额维度一致，见 `docs/topology-evaluation.md` §9）
- 槽位进程（SSH 隧道）与网关**解耦**：隧道挂了只是少一个槽，网关不重启
- 跳数与今天**完全相同**（用户→ECS→节点→Zen），延迟不劣

## 3. 需要你拍板的决策

### D1. win10-local 怎么办？（三选一）

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 在本机装 OpenSSH Server，与其它节点统一 | 装一次，开 2222 或 22 |
| B | 本机继续跑**完整旧网关**，只作为旧链路的桶；新网关暂不含它 | 少一个槽位，但零改动 |
| C | 本机跑独立 SOCKS5 守护（如 gost 静态包） | 多一个常驻进程要维护 |

> 注：本机 8791 端口的网关进程今天仍有故障（见 §6），选项 B 等于把它隔离在旧链路里。

### D2. 槽位出口机制

| 选项 | 说明 |
| --- | --- |
| **A（推荐）SSH 动态转发** | ECS 侧 `autossh -D <本地端口> user@node`；**节点侧零安装**（只要有 sshd）。已确认 owin10 / ubuntu26 / phone115 的 sshd 都可达 |
| B 节点跑 SOCKS5 守护 | ECS 侧无进程，直连 `node:1080`；但每台节点要装/维护一个二进制 |
| C 混合 | 服务器用 A，手机用 B |

### D3. 容器化粒度

| 选项 | 说明 |
| --- | --- |
| **A（推荐）3 容器** | `gw`（网关）+ `tunnels`（一个 supervisor 管 N 个 autossh）+ `watch`（可选健康/自愈）。compose 编排 |
| B 每槽一个容器 | 隔离最好，但 N 个手机就是 N 个容器，1.6 GB 内存吃不消 |
| C 只容器化网关 | 隧道跑在宿主 systemd；最省内存，但少了一层一致性 |

### D4. 槽位选择与容错策略（我按主流默认实现，你可否决）

- 逐槽：**在途上限**（防单槽打爆）+ **冷却**（429 → 指数退避 60s→…→封顶 15min）+ **熔断**（连续 5xx 达阈值）
- 选择：least-inflight 为主 + **闲置加权**（借鉴 `workbuddy2api`）
- **客户端错误不罚槽位**（400 畸形 JSON / 内容拦截）——今天 LB 会把它算作失败
- **全槽不可用 → 明确 503**（不是含糊的 502），并带上每个槽的最后错误
- 移动 IP 漂移（换网 = 新 IP = 新配额）视为**正常事件**，不告警

## 4. 分阶段执行计划

### 阶段 0 — 准备（不碰旧部署，可随时中止）
1. ECS 加 1–2 GB swap（`fallocate` + `mkswap` + `fstab`）
2. `apt install docker-compose-v2`
3. 建 `/opt/proxy_opencode_v2/{config,data,logs}`
4. Cloudflare 加 `llm2.223722.xyz` 隧道入口（**先不重启**，等网关起来再切）

**验收**：`docker compose version` 有输出；`free -m` 显示 swap；`dig llm2.223722.xyz` 有记录

### 阶段 1 — 代码（本仓库，走完整门禁）
1. `ZEN_PROXIES` 配置（逗号分隔，取代单值 `ZEN_PROXY`；空 = 直连）
2. 槽位池实现：`upstreams/slot_pool.py`（冷却/熔断/在途/加权选择）
3. `/admin/slots` 视图（每槽：出口、状态、冷却剩余、最近错误、成功率）
4. 单测覆盖：冷却、熔断、全灭 503、客户端错误不罚槽位、加权选择
5. 文档 + CHANGELOG（本项目硬约束）

**验收**：`pytest tests/ balancer/tests/` + `ruff` + `mypy` 全绿

### 阶段 2 — 槽位出口
1. ECS 生成密钥，授权到 ubuntu26 / owin10 / phone115
2. 手工验证单槽：`ssh -D 10801 …` + `curl --socks5-hostname 127.0.0.1:10801 ip-api.com` → **确认出口 IP 等于该节点的 IP**
3. 起 autossh supervisor，逐槽重复验证

**验收**：每个槽位报出的出口 IP 与 `docs/topology-evaluation.md` §1 的表格一致

### 阶段 3 — 新网关上线
1. 容器化（Dockerfile + compose）
2. 起 8793，**先只挂 slot 0（ECS 直连）**
3. 三协议各打一次（chat / responses / messages）+ 三客户端冒烟
4. 逐个加槽，每加一个观察 10 分钟
5. 切 `llm2.223722.xyz` → 8793

**验收**：`curl llm2.223722.xyz/healthz` 返回 200；`/admin/slots` 显示所有槽健康

### 阶段 4 — 并行观察（建议 ≥ 3 天）
1. 让 hermes / claude code / codex 一部分走 llm2，一部分仍走 llm
2. 对比：延迟、成功率、每槽分布、ECS 内存/流量
3. 记录任何槽位抖动

**验收**：新链路成功率 ≥ 旧链路，延迟不劣，无未解释的槽位掉线

### 阶段 5 — 切换与下线
1. 客户端 base_url 切到 `llm2.223722.xyz`
2. 观察期后：停旧 LB（7892）+ 4 桶的网关进程
3. **保留**节点上的 sshd（新网关要靠它做槽位）
4. 旧入口保留一段时间作为回滚路径

**验收**：旧进程停掉后新链路无影响

## 5. 成本提醒（提前说清楚）

- 路径：用户 → ECS → 节点 → Zen → 节点 → ECS → 用户，**ECS 双向各走一遍**
- 与今天 LB 中继的模式**流量相同**，不增加
- 但槽位变多时，ECS 出口带宽是线性成本项（阿里云按流量计费）
- **建议阶段 4 实测**：单次 agent 请求的 ECS 流量 × 预估请求量 → 估算月成本
  （参考：claude code 单请求上行 ~38 KB，agent 会话 10 轮 ≈ 400 KB）

## 6. 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 新网关有问题 | **旧链路完全没动**，回滚 = 客户端 base_url 指回 `llm.223722.xyz` |
| ECS 内存不足 | 加 swap + 容器 memory limit；扩槽时盯 `free -m` |
| 隧道层抖动 | autossh 自动重连；槽位健康检查快速剔除 |
| 手机桶休眠/被杀 | 当作**正常状态**设计（静默跳过 + 快速冷却），不告警不阻塞 |
| ECS 成为单点 | 阶段 5 后再考虑第二个 ECS 实例 + Cloudflare 负载均衡 |
| 已知故障未清 | **win10-local 的计划任务上下文仍有 connect 超时**（见 §7），新方案里它会变成一个纯 SSH 槽，绕开这个问题 |

## 7. 我的意见（不迎合，直说）

1. **方案方向对，容器化也对。** 它把「网关」和「出口点」解耦，正好治今天暴露的病：
   同一份代码在 4 台异构机器上跑，光部署方式就有 4 种，今天 win10-local 那个
   「同代码同 venv，交互会话 200 / 计划任务超时」的故障就是这类问题的典型。
2. **手机桶的最大风险不是技术，是运维噪音。** 手机休眠、Termux 被 Android 杀、
   移动 IP 漂移都会造成槽位抖动。必须**把「槽位随时消失」当正常状态设计**
   （静默跳过 + 快速冷却 + 全灭时明确 503），否则会像今天一样反复排查。
3. **建议分两步扩，不要一次铺满**：先上「ECS 直连 + 现有 3–4 个稳定节点」跑稳，
   再上手机。手机桶先加 1–2 台验证抖动模式，再规模化。
4. **建议给槽位加「质量分」**：移动 IP 抖动大，权重低一点；固定宽带的槽优先。
   这比纯 least-inflight 更抗抖动。
5. **ECS 1.6 GB 内存是硬约束**，扩到几十个槽位时要提前规划升配或分片。
6. **`win10-local` 建议选 D1-A（装 sshd）**，让它退化成一个纯出口槽——
   这样今天那个启动上下文的故障就自然消失了。
7. **不建议现在动旧链路**：双网关并行是稳的，但**不要**为了「干净」去改旧桶，
   那会把一个已经跑着的系统重新变成变量。
