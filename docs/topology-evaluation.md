# 拓扑评估：四桶分散 vs 统一部署到 ECS + 代理 IP

**结论先行**：把网关统一搬到 ECS 在技术上完全可行（实测机房 IP 能过 Zen 免费层门禁），
但**用代理 IP 去凑出 4 份配额**这条路，在「更成熟、更正规」这个目标上是**反的**。
真正成熟的做法是：**保留 IP 多样性（那是配额本身），把工程成熟度补齐**——而后者正好是
`workbuddy2api-ychzh` 做得更好的地方。

本文所有数字均为 2026-09-30 / 10-01 实测，可复现。

---

## 1. 先纠正一个前提假设

「机房 IP 会被免费层拦掉」——**实测不成立**。

| 节点 | 出口 IP | 国家/城市 | ISP | 类型 | Zen 门禁 |
| --- | --- | --- | --- | --- | --- |
| win10-local | 111.55.74.57 | 中国 / 昆山 | 中国移动 | mobile=true, hosting=false | ✅ 200 |
| owin10 | 218.93.250.242 | 中国 / 南京 | 中国电信 | mobile=false, hosting=false | ✅ 200 |
| ubuntu26 | 36.149.54.82 | 中国 / 南京 | 中国移动 | mobile=true, hosting=false | ✅ 200 |
| phone115 | （手机移动网络） | 中国 | 中国移动 | mobile | ✅ 200 |
| **ECS** | **47.250.130.52** | **马来西亚 / 吉隆坡** | Alibaba (US) | **hosting=true** | **✅ 200（连续两次）** |

ECS 是**阿里云机房 IP**，用 0.6.2 的完整上行体（bridge note + 两个最小内置 schema +
`stream:true`）连打两次，**都是 200**。所以「机房 IP 不行」是错的。

顺带一个反直觉的发现：四个桶**全部是国内家宽/移动 IP**，`ubuntu26` 名字像云主机，
出口其实是南京移动的移动网络。

## 2. 延迟：机房出口不比国内出口慢

直连 Zen（绕过 LB），各 5 次采样：

| 出口 | TTFB 中位 | 总耗时中位 |
| --- | --- | --- |
| ECS 马来西亚机房 | 1,653 ms | **1,896 ms** |
| ubuntu26 国内移动 | 1,639 ms | **1,891 ms** |

**基本持平。** 上游是 Cloudflare（`172.65.90.x`），马来西亚到 CF 边缘不比南京到 CF 边缘差。

> 对照：走公网入口（中国客户端 → Cloudflare → ECS → Tailscale → 桶 → Zen）
> 的端到端总耗时中位是 **5,082 ms**。也就是说，**当前拓扑的最大延迟来源是
> Tailscale 那一跳**，不是出口 IP 本身。ECS 恰好是 ubuntu26 的 Tailscale 中继
> （`gw-kl` = 吉隆坡），所以绕远路的问题在 ubuntu26 上尤其明显。

## 3. 配额：这才是四桶存在的唯一理由

免费额度**按出口 IP 计**。所以：

- 4 个桶 = 4 个出口 IP = **4 份配额**
- 网关搬到 ECS 一台 = **1 个出口 IP = 1 份配额**，容量**直接降到 1/4**
- ECS + 代理 IP 池 = N 份配额，但见下节

**分散部署不是架构偏好，是计费模型的直接推论。** 想「统一部署」就必须同时解决
「怎么变出 N 个出口 IP」，否则是净减容。

## 4. 代理 IP 这条路：技术上可行，方向上不对

| 维度 | 评估 |
| --- | --- |
| 技术可行性 | 可行。ECS 已经证明能过门禁，加 `ZEN_PROXY` 或按目标 IP 分流即可 |
| **成本** | **从 0 变成持续支出**。现在 4 个出口 IP 是你已有的家宽/移动/手机，边际成本 0；商用代理按流量或 IP 计费 |
| IP 质量 | 机房代理 IP 是**最容易被风控标记**的一类——住宅代理之所以贵，正是因为机房段被大规模滥用。你现在这套住宅/移动 IP 反而是稀缺资源 |
| 延迟 | 多一跳，通常 +100–300 ms（而且不稳定） |
| 可用性 | 新增一个故障域：代理池挂了，全部桶一起挂。现在是 4 个独立故障域 |
| **合规** | **这条最要紧**：`CONTRIBUTING.md` 明确把「风控绕过、免费额度滥用」列为禁止事项。用代理 IP 池去倍增免费额度，正是这个描述本身 |

「更正规」这个目标，在代理这条路上是**反方向**的。真正让它「正规」的是：
**用的都是你自己真实持有的出口**（家宽、手机），而不是伪装出来的 IP。

## 5. 那么「统一部署」到底值不值

把问题拆成三层，答案就不一样了：

| 层 | 建议 | 理由 |
| --- | --- | --- |
| **LB（控制面）** | ✅ **已经在 ECS 上，保持** | 公网稳定 IP、常开、TLS 终结，位置正确 |
| **网关（数据面）** | ⚠️ **ECS 可以作为「第 5 个桶」，而不是替代品** | 实测能过门禁、延迟不劣、常开、运维简单；但**不要撤掉现有的 4 个出口**，否则容量 -75% |
| **出口 IP 多样性** | ✅ **保留** | 这是配额的载体，不是可优化项 |

### 推荐的演进方向

1. **在 ECS 上跑一个网关实例**（和 LB 同机），作为第 5 个上游。
   - 净增 1 份配额（4 → 5），不是减容
   - 命中 ECS 桶的请求**省掉整个 Tailscale 跳**，端到端预计从 ~5.1s 降到 ~3.4s
   - 这一步同时把「统一部署」想要的好处（一处部署、一处监控、常开）拿到
2. **把家宽桶降级为「尽力而为」容量**：它们免运维成本、但会抖
   （见 §6 的实测故障），LB 已经能自动跳过，不需要为它们做额外保障
3. **不要买代理 IP**。要扩容优先考虑：再申请一台境外小机器（自建、干净的机房 IP、
   实测可过门禁），比买代理池便宜、可控、也不踩自己写的红线

## 6. 一个反面教材：家宽桶的脆弱性是真实成本

评估「集中 vs 分散」时，这是**支持集中**的最有力证据，值得单独记一笔。

2026-10-01 00:29 起，**win10-local 桶持续 502**。排查过程：

| 假设 | 验证 | 结论 |
| --- | --- | --- |
| 代码 bug | 同一份代码、同一 venv、换端口在我的会话前台跑 → **200 / 1.69 s** | ❌ 不是代码 |
| `trust_env` 跟随环境代理 | 复现：带 `HTTP_PROXY=http://127.0.0.1:7897`（已失效的 Clash）→ 失败 2.3 s，与线上 2.0 s 吻合 | ✅ **已修**（`UPSTREAM_TRUST_ENV` 默认 false） |
| IPv6 无路由 | 直连 IPv6 立即失败（0.00 s），IPv4 0.20 s 成功 | ❌ 不是主因 |
| TUN 网卡按进程分流 | 无 TUN 适配器，单一默认路由（WLAN → 192.168.1.1） | ❌ 排除 |
| **启动上下文** | **同代码同 venv：交互会话 200，计划任务上下文 connect 超时** | ✅ **根因在此层** |

即：**问题出在「计划任务 / pythonw 的启动上下文」，不在网关代码**。
修掉 `trust_env` 是必要的一步（去掉了一个确定的失败模式），但那台机器的启动
上下文仍有独立的网络故障待人工处理（Windows 防火墙对 `pythonw.exe` 的规则 /
计划任务的登录上下文是首要怀疑对象）。

这正是「四台异构家用机器 + 四种重启方式」的真实运维代价：
**同样的代码，在不同启动上下文里的网络行为可以完全不同。**

## 7. 参考 `workbuddy2api-ychzh`：真正值得学的部分

那个仓库是 36.8k 行 Go 的多账号网关，架构成熟度明显更高。它的「桶」是**账号**
（配额按账号），proxy_opencode 的「桶」是 **IP**（配额按 IP）——约束不同，
但**池化调度的工程模式完全可迁移**。

按性价比排序，建议吸收：

1. **错误分类统一入口 + 处置表**（`internal/pool`）
   按「余额耗尽 → session 失效 → 限流文案 → 状态码」的优先级分类，每一类有明确的
   账号处置与恢复路径。**关键设计：客户端造成的错误（400 畸形 JSON、内容拦截）
   不罚账号**——「问题在请求内容而非账号健康」。proxy_opencode 目前把 400/403
   一并算进失败，容易误伤健康桶。
2. **两条独立的退避线**：软冷却（`soft_rate × 2^(连续次数-1)`，封顶 `soft_rate_max`）
   与熔断器（`breaker_threshold` 连续失败 → `cooldown × 2^retryCount`，封顶 6h），
   计数独立、成功清零。proxy_opencode 0.6.2 刚引入的固定冷却窗口（900 s）是这条
   路的第一步，下一步就是「按连续次数指数退避 + 封顶」。
3. **选号策略的分层**：过滤 → 成本分层 → 最早到期优先 → 加权随机
   （`weight = credits 比例 × 10 + idleWeight`，`idleWeight = min(闲置小时 × 0.5, 5.0)`）
   → **防惊群（跳过 100 ms 内刚被选中的账号）**。proxy_opencode 的 LB 是纯
   least-connections，没有闲置加权，也没有防惊群。
4. **请求级结构化日志**：一行一请求，含 TTFB / 输出 tok / tok/s / 账号 uid 前缀，
   且**明确不含任何 token 明文**。proxy_opencode 已有 ttfb/total，缺 tok/s 与上游标识。
5. **livecfg 配置热更新**：面板改配置即时生效，不用重启。proxy_opencode 改环境变量
   必须重启（4 台机器 4 种重启方式，代价被放大）。
6. **Docker 一键部署 + 健康检查**：`docker-compose` + 内置 `HEALTHCHECK`，
   把「四台异构机器四种启动方式」压成一种。
7. **会话粘性**（`session_sticky`，TTL 30 m + Redis 镜像）
   —— 但**对 proxy_opencode 而言这条优先级低**：实测 Zen 的 prompt 缓存是
   **全局的、不绑出口 IP**（跨桶命中仍 99.9 %），所以「跨桶丢缓存」这个动机不存在。
   保留它只对「多轮对话中途换桶导致的状态抖动」有价值。

> 那个仓库的 README 里有一段「使用声明」，明确反对批量注册小号、转售配额、
> 加壳收费。它和 `CONTRIBUTING.md` 的红线是同一件事：**这套工具的自用边界**。
> 评估「代理 IP 扩容」时，值得把这段读一遍。

## 8. 一句话总结

| 问题 | 答案 |
| --- | --- |
| 机房 IP 会被拦吗？ | 不会，实测 200 |
| 统一部署到 ECS 更成熟吗？ | **部署面更成熟，容量面更差**（4 份配额 → 1 份） |
| 用代理 IP 走 4 份流量更正规吗？ | **不**。更贵、更慢、更易被标记、新增单点，且违反本仓库自己的红线 |
| 该怎么做？ | **ECS 加一个网关实例当第 5 个桶**（净增容量 + 省掉 Tailscale 跳），家宽桶降级为尽力而为，把 `workbuddy2api` 的池化语义（错误分类 / 双退避线 / 加权选桶 / 防惊群 / 热更新 / Docker）搬过来 |
| 最大的收益点 | 不是换出口，而是**去掉 Tailscale 那一跳**（当前端到端 5.1 s，直连出口仅 1.9 s） |
